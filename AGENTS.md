# AGENTS.md

Конфигурация для AI-агентов в проекте  
**Интеграция**: OpenCode + agency-agents + agent-skills  
🚨 **Этот файл ОБЯЗАТЕЛЕН к исполнению всеми агентами**

---

## 🎯 Orchestration Model (3 слоя)

Этот репозиторий имеет три композитных слоя с разными задачами:

| Слой | Расположение | Назначение | Правило |
|------|-------------|-----------|---------|
| **Skills** | `skills/<name>/SKILL.md` | Workflows с шагами и критериями выхода | **The HOW** — обязательные этапы при совпадении intent |
| **Personas** | `agents/<role>.md` | Роли с перспективой и форматом вывода | **The WHO** — не вызывают друг друга |
| **Slash Commands** | `.claude/commands/*.md` или эмуляция через навыки | Пользовательские entry points | **The WHEN** — слой оркестрации |

### 📐 Composition Rule
**Пользователь (или slash-команда) — оркестратор.**  
- ❌ Personas **НЕ** вызывают других personas
- ✅ Persona **МОЖЕТ** вызывать skills
- ✅ Единственный multi-persona паттерн — **parallel fan-out** с merge-шагом (используется в `/ship`)

## 🔧 Skill Execution Rules

### Skill Path Configuration
Skills расположены:
- **Primary**: `.opencode/skills/<skill-name>/SKILL.md` (относительно корня проекта)
- **Fallback**: `/mnt/skills/user/<skill-name>/SKILL.md`

Если skill не найден по имени — рекурсивно искать в локальной директории `.opencode/skills/`.

### Core Rules
1. Если задача совпадает со skill — **ОБЯЗАТЕЛЬНО** вызвать его
2. **НИКОГДА** не реализовывать напрямую, если применим skill
3. **ВСЕГДА** следовать инструкциям skill точно (не частично)
4. Переходить к реализации только после завершения обязательных шагов (spec, plan и т.д.)

### Intent → Skill Mapping

| User Intent | Skill | Output |
|-------------|-------|--------|
| Новая фича / функциональность | `spec-driven-development` → `incremental-implementation` → `test-driven-development` | Spec + Code + Tests |
| Планирование / декомпозиция | `planning-and-task-breakdown` | Plan в `plans/{task-name}.md` |
| Баг / ошибка / неожиданное поведение | `debugging-and-error-recovery` | Fix + тесты |
| Code review | `code-review-and-quality` | Отчёт + фиксы |
| Рефакторинг / упрощение | `code-simplification` | Refactored code + бенчмарки |
| API / интерфейс дизайн | `api-and-interface-design` | API spec + примеры |
| UI / фронтенд работа | `frontend-ui-engineering` | Компоненты + стили |

### Lifecycle Mapping (Implicit Commands)
OpenCode не поддерживает slash-команды напрямую (`/spec`, `/plan` и т.п.).  
Агент **внутренне** следует этому lifecycle:

```
DEFINE → spec-driven-development
PLAN → planning-and-task-breakdown
BUILD → incremental-implementation + test-driven-development
VERIFY → debugging-and-error-recovery
REVIEW → code-review-and-quality
SHIP → shipping-and-launch (parallel fan-out)
```

### 🚫 Anti-Rationalization (Запрещённые оправдания)

| Оправдание | Почему неправильно | Правильное действие |
|-----------|-------------------|-------------------|
| «Это слишком мелкая правка для навыка» | Нарушает консистентность | Всегда проверять `skills/` перед действием |
| «Я быстро реализую без спецификации» | Риск несоответствия требованиям | Сначала `spec-driven-development`, потом реализация |
| «Сначала соберу контекст» | Пропуск обязательных шагов | Сразу вызывать skill |
| «Протестирую потом» | Технический долг | Тесты — часть критериев приёмки |
| «Логирование замедлит работу» | Теряется аудит | `PROGRESS.md` — обязательный шаг |

## 📝 Project Logging (ОБЯЗАТЕЛЬНО)

### PROGRESS.md — КРИТИЧЕСКИ ВАЖНО

**Агент ОБЯЗАН вести журнал в ОБРАТНОМ ХРОНОЛОГИЧЕСКОМ ПОРЯДКЕ (Reverse-Chronological).**  
Самые актуальные записи — всегда в самом начале файла (сразу после шапки).

🚫 **ЗАПРЕЩЕНО**:
- Добавлять записи в конец файла
- Искать "последнюю строку" или использовать `append`
- Выдумывать время (использовать системное)

#### 📐 Формат записи

**Перед изменением файлов:**
```markdown
### [YYYY-MM-DD HH:MM] <Краткое описание>
- Файл: `путь/к/файлу`
- Действие: планируемое_изменение
- Суть: <одно-два предложения о цели>
- Статус: [PLANNED]
```

**После выполнения:**
```markdown
### [YYYY-MM-DD HH:MM] <Краткое описание>
- Файл: `путь/к/файлу`
- Действие: <создан/изменён/удалён/перемещён>
- Суть: <результат изменения>
- Статус: [DONE] | [ERROR: причина] | [PARTIAL: что не сделано]
- Следующий шаг: <опционально>
```

#### 🛠 Алгоритм обновления (ОБЯЗАТЕЛЕН)
1. Прочитать `PROGRESS.md`
2. Найти маркер `<!-- LOG_START -->`
3. Сгенерировать новую запись
4. **ЗАПИСАТЬ ФАЙЛ ЦЕЛИКОМ**: `Шапка` + `---` + `<!-- LOG_START -->` + `\n` + **НОВАЯ ЗАПИСЬ** + `\n` + `Все старые записи` + `<!-- LOG_END -->`

#### 🚫 Запрещённые действия при логировании
- Искать конец файла или последнюю запись
- Использовать `append` или `insert at line X`
- Оставлять пустые строки, сбивающие порядок
- Менять системное время на выдуманное

#### 📋 Шаблон PROGRESS.md (создать, если отсутствует)
```markdown
# PROGRESS.md

> Автоматический журнал изменений агента  
> Формат времени: `YYYY-MM-DD HH:MM` (системное время)  
> Статусы: `[PLANNED]` → `[DONE]` | `[ERROR: причина]` | `[PARTIAL: детали]`

## Сессия: {дата}

---
<!-- LOG_START -->

### [2026-06-20 00:00] Инициализация сессии
- Файл: `PROGRESS.md`
- Действие: создан
- Суть: Начало работы агента с проектом
- Статус: [DONE]

<!-- LOG_END -->
```

## 🎭 Persona Rules

### Файлы персон
Расположены в `.opencode/agents/` или `agents/`:

| Персона | Файл | Когда активировать |
|---------|------|-------------------|
| `@security-auditor` | `agents/security-auditor.md` | Проверка криптографии, токенов, разрешений |
| `@code-reviewer` | `agents/code-reviewer.md` | Проверка качества кода |
| `@test-engineer` | `agents/test-engineer.md` | Написание тестов |
| `@backend-specialist` | `agents/backend-specialist.md` | Server-side логика, API, БД |
| `@frontend-specialist` | `agents/frontend-specialist.md` | UI компоненты, стили |
| `@tech-writer` | `agents/tech-writer.md` | Документация, комментарии |

### 📌 Правила для персон
1. **НЕ** вызывают других персон
2. **МОГУТ** вызывать skills
3. Работают как subagents (auto-discovered из `agents/`)
4. Не могут вкладываться друг в друга (no nesting)

### Task Delegation (Parallel Fan-Out)
Единственный поддерживаемый multi-persona паттерн — параллельный запуск с merge:

```
/ship → Запустить параллельно:
  ├─ code-reviewer
  ├─ security-auditor
  └─ test-engineer
→ Синтез отчётов
```

⚠️ **НЕ** создавать "router" persona, которая решает, кого вызвать — это задача slash-команд и intent mapping.

## 📦 Context Efficiency Best Practices

Skills загружаются on-demand — только name и description при старте. Полный `SKILL.md` загружается только когда агент решает, что skill релевантен.

### Правила минимизации контекста
- ✅ **Держать SKILL.md под 500 строк** — детальную справку выносить в отдельные файлы
- ✅ **Писать специфичные описания** — чтобы агент точно знал, когда активировать skill
- ✅ **Использовать progressive disclosure** — ссылаться на вспомогательные файлы, которые читаются только при необходимости
- ✅ **Предпочитать скрипты inline-коду** — выполнение скрипта не потребляет контекст (только вывод)
- ✅ **Ссылки на файлы работают на один уровень вглубь** — линковать напрямую из SKILL.md

## 🔄 Execution Model

Для каждого запроса:
1. Определить, применим ли какой-либо skill (даже если есть 1% вероятность)
2. Вызвать соответствующий skill через `skill` tool
3. Строго следовать workflow skill
4. Переходить к реализации только после завершения обязательных шагов (spec, plan и т.д.)

### Process Implementation Workflow

Когда пользователь говорит «реализуй», «исправь», «добавь»:

#### Шаг 1: Проверка контекста
- [ ] Есть ли спецификация в `specs/`? Если нет → создать через `spec-driven-development`
- [ ] Проверить `PROGRESS.md` на дублирующие задачи
- [ ] Определить приоритет: 🔴 Критический / 🟡 Важный / 💭 Незначительный

#### Шаг 2: Вызов навыка
```bash
# Всегда использовать skill-инструмент
skill incremental-implementation --spec specs/{путь}/spec.md
```

#### Шаг 3: Верификация и логирование
- [ ] Код соответствует спецификации
- [ ] Тесты добавлены/обновлены
- [ ] Нет новых warning/error в логах
- [ ] **Обязательно**: Запись в `PROGRESS.md` с `[DONE]`/`[ERROR]`/`[PARTIAL]`

## ✅ Чеклист перед завершением задачи

Перед тем как сообщить пользователю о завершении:

- [ ] Все изменения задокументированы в `PROGRESS.md` с корректным временем
- [ ] Код соответствует спецификации (если была)
- [ ] Тесты добавлены/обновлены и проходят
- [ ] Нет новых security-предупреждений
- [ ] Изменения протестированы локально или через CI
- [ ] Если задача частичная — чётко указано, что осталось сделать

## 📎 Приложения

### А: Команды для генерации времени
```bash
# Linux/macOS
date "+%Y-%m-%d %H:%M"

# Windows (PowerShell)
Get-Date -Format "yyyy-MM-dd HH:mm"

# В коде агента: использовать системный вызов, НЕ хардкодить
```

### Б: Структура спецификаций (для Roadmap.md)

При работе с анализом из `Roadmap.md`:

```
specs/
├── 1-Архитектура/
│   └── spec.md
├── 2-Инфраструктура/
│   └── spec.md
└── ...
```

**Формат spec.md:**
```markdown
# Spec: {Название пункта из Roadmap}

## Источник
- Отчёт: Roadmap.md
- Раздел: {номер}.{подномер}
- Файлы: `список/затронутых/файлов`

## Проблема
{Описание из отчёта}

## Требования
- [ ] Требование 1
- [ ] Требование 2

## Критерии приёмки (Verification)
- [ ] Тесты проходят
- [ ] Нет регрессий
- [ ] PROGRESS.md обновлён

## Ссылки
- [Roadmap.md#раздел](../Roadmap.md#{якорь})
```
